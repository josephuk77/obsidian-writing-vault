# [Timing Jeju 개발기 2] DB 적재 경계와 일정 무결성

이번에는 기능 하나를 더 붙이기보다, 앞으로 외부 데이터를 안전하게 넣을 수 있는 DB 경계를 먼저 다듬는 쪽에 가깝게 작업했다.

기존 스키마만으로도 테이블은 꽤 갖춰져 있었지만, 실제로 TourAPI나 TAGO, KMA 응답을 받아 적재하려고 보면 어디까지를 raw로 보관하고 어디부터 정규화해서 읽을지, 또 어떤 제약으로 잘못된 연결을 막을지가 더 중요했다.

특히 일정 쪽은 여행, 일정 버전, Day, item, leg, 계산 결과가 서로 맞물려 있어서 한 군데만 느슨해도 다른 여행 데이터가 섞이거나 확정된 일정이 뒤에서 다시 바뀌는 문제가 생길 수 있었다.

## DB 적재 경계

이번에 가장 먼저 정리한 건 외부 응답을 바로 공개 조회 테이블에 덮어쓰지 않는 구조였다.

수집 실행은 `data_import_runs`에 남기고, 원문 응답은 `external_api_snapshots`에 snapshot으로 보관한 다음, 검증과 파싱을 통과한 값만 장소, 교통, 날씨 read model에 반영하는 흐름으로 고정했다.

이렇게 해두면 나중에 importer를 붙일 때도 "어떤 원문을 기준으로 이 행이 만들어졌는지"를 역으로 따라갈 수 있다. 그래서 정규화 테이블에는 `import_run_id`와 `source_snapshot_id`를 같이 연결하고, provider·service·operation·scope가 맞지 않으면 DB에서 바로 거부하도록 제약을 강화했다.

checkpoint도 같이 손봤다. 같은 범위의 성공한 실행만 마지막 성공 지점으로 승격할 수 있게 막아 두지 않으면, 실패한 실행이나 부분 성공 실행이 기준점을 덮어쓰는 상황이 생길 수 있기 때문이다.

## 일정 무결성

일정 쪽에서는 확정된 버전이 뒤에서 흔들리지 않게 막는 작업이 컸다.

candidate나 active 상태가 된 일정은 Day의 날짜와 시간 창, item과 leg 연결이 뒤늦게 바뀌면 안 된다. 그래서 일정 봉인 이후에는 Day 변경과 교차 참조를 더 엄격하게 막고, 다른 여행이나 다른 일정 버전의 행이 계산 결과에 섞이지 않도록 복합 FK를 더 촘촘하게 걸었다.

`trip_schedule_versions`의 base도 아무 버전이나 가리키지 못하게 했다. 같은 여행 안에서 더 작은 `version_no`만 참조하도록 제한해서, 버전 계보가 꼬이거나 순환 참조가 생기는 가능성을 줄였다.

이 부분은 겉으로 바로 보이는 기능은 아니지만, 추천 후보나 날씨 영향, 이동 구간 계산이 일정 버전과 Day를 정확히 공유하도록 만드는 데 필요했다.

## 최신 원천 필드 반영

외부 API 문서도 이번 작업 범위 안에서 같이 맞췄다.

TourAPI 쪽은 기존 지역 코드와 분류 코드를 그대로 믿고 가기보다, 최신 KorService2 기준의 법정동 코드와 신분류 필드를 스키마와 매핑 문서에 반영했다. 나중에 importer를 붙일 때 예전 필드와 새 필드가 뒤섞여 해석되는 일을 줄이기 위해서였다.

TAGO 쪽도 정류장, 노선, 시간표를 단순 ID 하나로만 연결하지 않고 provider와 도시 범위를 같이 보는 쪽으로 정리했다. 원천이 다른 데이터를 같은 키로 잘못 합치는 상황을 DB에서 먼저 막겠다는 판단이었다.

## 검증 결과

이번 작업은 문서만 고친 날은 아니었다. 같은 브랜치에서 테스트 계약 추가, 무결성 리팩터링, 문서 정리까지 세 커밋을 한 번에 밀어 넣었다.

확인 과정에서는 Python unittest 75개가 통과했고, SQL 정책 검사 위반은 0건으로 정리됐다. PostgreSQL 16/PostGIS Docker와 Supabase PostgreSQL 17 양쪽에서 같은 migration 순서를 적용해 스키마 계약과 음수 제약을 같이 확인했다.

결과적으로 이번 변경으로 importer 자체가 바로 생긴 것은 아니다. 대신 importer를 붙였을 때 raw 응답, 정규화 데이터, 일정 계산 결과가 서로 어떤 경계에서 만나야 하는지는 한 번 더 분명해졌다.
