# [Timing Jeju 개발기 1] 저장소 분리와 인증 경계

Timing Jeju 백엔드 작업을 본격적으로 밀어 넣은 날이었다.

이날은 단순히 Spring Boot 프로젝트 하나를 만든 정도가 아니라, 앞으로 기능을 올릴 수 있는 기준선을 먼저 정리하는 쪽에 가까웠다.

초반에는 백엔드 저장소 자체를 어떻게 나눌지부터 손봤다.
Spring API는 `services/spring-api`로 옮기고, FastAPI MCP는 같은 제품이지만 다른 실행 경계로 다루도록 분리했다.
같은 저장소 안에 두더라도 빌드, 품질 게이트, 문서 계약이 한쪽에 끌려가지 않게 만드는 게 먼저 필요했다.

이 작업을 하면서 FastAPI MCP는 결국 별도 저장소로 떼어냈다.
`Timing-Jeju/jeju_AI` 저장소를 따로 두고 Python 3.12, uv 잠금, Ruff, pytest 중심의 독립 CI를 잡았다.
백엔드 저장소에서는 Spring 코드와 공통 계약만 남기고, FastAPI 구현 파일과 Python 의존성은 걷어냈다.
한 제품을 여러 저장소로 나눌 때 제일 신경 쓴 부분은 “어디까지가 공통 기준이고 어디서부터가 서비스 책임인가”를 문서와 테스트로 같이 고정하는 일이었다.

그 다음은 로컬 개발 환경과 운영 환경을 섞지 않도록 Supabase 경계를 정리했다.
로컬에서는 Supabase Auth와 PostgreSQL/PostGIS를 바로 띄워 확인할 수 있게 하고, 운영 마이그레이션은 `auth` 스키마를 건드리지 못하게 분리했다.
운영 SQL이 잘못 들어가면 인증 계층까지 같이 흔들릴 수 있어서, SQL 정책 검사 스크립트와 테스트를 따로 붙여 우회 케이스까지 막았다.
주석으로 규칙을 피해 가는 경우나 여러 대상을 한 번에 지우는 경우도 전날 커밋 범위 안에서 같이 보완했다.

이날 가장 비중이 컸던 구현은 인증 경계였다.
Spring Security OAuth2 Resource Server를 기준으로 Supabase JWT를 검증하고, `/api/v1/**` 경로를 보호하는 공통 기반을 만들었다.
여기서 중요했던 건 로그인 기능을 빨리 만드는 것보다, 토큰이 어떤 조건일 때 통과하고 어떤 조건일 때 바로 막혀야 하는지를 먼저 좁히는 일이었다.

그래서 JWKS 기반 검증과 `local-hs256`용 로컬 전략을 나눴고, `iss`, `aud`, `role`, `sub`, `exp`, `nbf` 같은 claim을 엄격하게 확인하도록 만들었다.
`anon`, `service_role`, 잘못된 issuer, 이상한 subject, 중복 Authorization 헤더처럼 애매하게 넘어갈 수 있는 경우도 바로 거부하도록 정리했다.
에러 응답도 그냥 401 하나로 뭉개지 않고, 토큰 오류와 접근 거부를 구분한 JSON 계약으로 맞췄다.

구현을 진행하면서 CORS도 꽤 많이 손봤다.
허용 Origin을 문자열로만 들고 가면 브라우저가 실제로 직렬화하는 Origin과 어긋나는 경우가 생길 수 있어서, 기본 포트 정규화와 숫자형 host 경계를 보완했다.
특히 브라우저와 다르게 해석될 수 있는 비정규 IPv4, IPv6, 16진 숫자형 host, trailing dot 케이스를 startup 단계에서 fail-fast로 막았다.
이 부분은 겉으로 보이는 기능은 아니지만, 나중에 운영에서 “어떤 Origin은 되고 어떤 Origin은 안 되는” 애매한 상태를 줄이는 데 필요했다.

현재 사용자 정보도 Spring `Jwt` 객체를 그대로 끌고 다니지 않도록 작게 감쌌다.
도메인이나 애플리케이션 계층에서는 `CurrentUser` 계약만 보게 하고, SecurityContext와 JWT 해석은 보안 어댑터 안에 묶어 두었다.
이렇게 해 두면 이후 기능이 늘어나더라도 인증 프레임워크 세부사항이 서비스 코드 안쪽으로 새지 않는다.

결과적으로 이날 원격에 반영된 작업은 크게 세 갈래였다.
백엔드 초기 기준선 구축, FastAPI MCP 저장소 분리, 그리고 Supabase JWT 인증 경계 구현이다.
`Timing-Jeju/jeju_BE`에서는 PR `#2`, `#4`, `#6`, `#8`이 머지됐고, `Timing-Jeju/jeju_AI`에서는 PR `#2`가 머지됐다.
커밋 수로 보면 백엔드 쪽 29건과 AI 저장소 5건이 같은 날짜 범위에 확인됐다.

이날 작업을 지나고 나서야 Timing Jeju는 “코드를 시작한 저장소”에서 “이제 기능을 올릴 수 있는 저장소”에 가까워졌다.
처음 기능 하나를 만드는 날보다 느릴 수는 있어도, 저장소 경계와 인증 규칙을 먼저 세워 둔 쪽이 뒤에서 덜 흔들린다고 판단했다.
