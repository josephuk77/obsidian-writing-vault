# [FaithLog 개발기 7] 서비스 클래스를 나누고 보안을 다시 확인했다

이번 주에는 기능을 거의 추가하지 않았다.

기능을 계속 만들다 보니 서비스 클래스가 너무 커졌기 때문이다.

처음에는 한 클래스에 로직이 모여 있는 것이 찾기 편했다. 그런데 조회 하나를 수정하려고 해도 상태 변경과 권한 로직까지 같이 확인해야 했다. 테스트도 어디까지 실행해야 하는지 애매해졌다.

결국 한번 나누고 가기로 했다.

## 어디서부터 나눌지 고민했다

처음에는 Controller, Service, Repository 중심으로 패키지를 나눴다. 기능이 적을 때는 이해하기 쉬웠지만 도메인이 커지자 거대한 서비스 클래스가 생겼다.

캠퍼스 관리, 납부 명령, 납부 조회, 경건생활, 투표, 알림을 각각 유스케이스 단위로 분리했다. 조회와 변경도 가능한 범위에서 나눴다. 리팩터링 중에는 패키지 이동 때문에 테스트가 실행 순서에 따라 실패하거나, 공유 H2 데이터가 다른 테스트의 Spring Context를 오염시키는 문제를 해결했다.

### 알림은 발송과 대상을 분리했다

FCM 발송 자체와 “누구에게 언제 알릴 것인가”를 분리했다. 외부 전송 실패가 핵심 트랜잭션을 되돌리지 않도록 경계를 조정하고, 중복 발송 방지 키와 잠금 만료 정책을 테스트로 남겼다.

Docker 이미지 빌드 중에는 BuildKit 메타데이터 I/O 오류도 만났다. 애플리케이션 컴파일 문제가 아니라 Docker 저장소 계층 문제였고, 호스트 디스크 여유 공간이 매우 적었다. 사용자 데이터나 볼륨을 임의로 지우지 않고 통합 QA 단계로 이관했다.

## 리팩터링보다 오래 걸린 Refresh Token 문제

동일한 Refresh Token으로 두 요청을 동시에 보내자 두 요청이 모두 성공하는 문제가 재현됐다. Redis에서 기존 JTI를 읽는 `GET`과 새 JTI를 저장하는 `SET`이 분리되어 있었기 때문이다. 두 요청이 동시에 기존 값을 읽으면 모두 검증을 통과할 수 있었다.

비교와 교체를 Redis Lua 스크립트 하나로 수행하도록 바꿨다. 승자만 새 토큰을 받고 패자는 거부되며, 충돌이 감지된 세션은 폐기 표식을 남겨 이미 발급된 Access Token도 더 이상 인증에 사용되지 않게 했다. 동시 요청 테스트의 결과는 `[200, 200]`에서 `[200, 401]`로 바뀌었다.

처음에는 패자 요청만 401로 막으면 된다고 생각했다. 하지만 경쟁 요청에서 이미 발급된 Access Token은 계속 사용할 수 있었다. 그래서 refresh 교체 실패만 처리하지 않고 세션 단위로 access도 폐기하도록 범위를 넓혔다. 동시성 문제를 한 요청의 성공·실패만 보고 판단하면 안 된다는 것을 알게 됐다.

## 이왕 시작한 김에 보안도 다시 확인했다

권한 매트릭스와 위협 모델을 만들고 다음 항목을 점검했다.

- 다른 캠퍼스 ID를 바꿔 넣는 IDOR 공격
- 역할 변경 뒤 기존 JWT가 계속 유효한 문제
- 민감 정보가 로그나 오류 응답에 노출되는지
- 입력값 검증과 예외 응답의 일관성
- 배포 의존성과 공급망 위험
- Supabase와 데이터베이스의 외부 접근 경계

인가 테스트는 “관리자는 성공한다”보다 “다른 캠퍼스의 관리자는 실패한다”를 더 중요하게 다뤘다.

특히 URL의 `campusId`만 다른 값으로 바꿔도 조회되는 IDOR 문제가 없는지 도메인별로 확인했다. 역할 이름만 확인하지 않고, 요청한 사용자가 실제로 해당 캠퍼스에 속해 있는지까지 검증하도록 했다.

파일을 나누는 것 자체는 어렵지 않았다.

어려웠던 것은 어떤 로직을 같이 두고 어떤 로직을 분리할지 결정하는 일이었다. 잘못 나누면 파일만 많아지고 오히려 흐름을 찾기 어려워질 수 있었다.

그래도 이번에 권한과 트랜잭션 범위를 다시 정리하면서 이후 기능을 추가할 위치는 전보다 명확해졌다.

Refresh Token 동시성 문제는 별도 글로 더 자세히 정리해도 좋을 것 같다.
