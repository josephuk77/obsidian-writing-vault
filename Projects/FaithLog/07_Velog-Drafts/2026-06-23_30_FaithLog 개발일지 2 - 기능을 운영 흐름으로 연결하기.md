# [FaithLog 개발기 5] 따로 만든 기능을 실제 운영 흐름으로 연결했다

지난주까지는 이슈 하나를 잡고 기능 하나를 만드는 식으로 진행했다.

그런데 이렇게 하다 보니 각각의 API는 동작해도 실제 사용 흐름이 자연스러운지는 잘 모르겠다는 생각이 들었다.

예를 들어 커피 투표만 만드는 것은 어렵지 않다. 하지만 실제로는 담당자를 정하고, 투표를 만들고, 사용자가 메뉴를 고르고, 투표가 끝나면 돈을 청구하는 데까지 이어져야 한다.

이번에는 이런 흐름을 연결하는 작업을 했다.

## Compute Engine 대신 Cloud Run을 선택한 이유

백엔드를 어디에 배포할지도 고민했다.

처음에는 Google Compute Engine에 직접 서버를 띄우는 방법을 생각했다. 서버를 직접 관리할 수 있고 익숙한 방식이라는 장점이 있었다.

하지만 FaithLog의 예상 사용자는 최대 600명 정도다.

하루 종일 요청이 계속 들어오는 서비스도 아니다. 경건생활을 체크하거나 투표가 열렸을 때 요청이 몰리고, 사용하지 않는 시간에는 요청이 거의 없을 것으로 예상했다.

이런 서비스에 Compute Engine을 사용하면 요청이 없는 시간에도 인스턴스를 계속 실행해야 한다. 현재 규모에서는 사용한 만큼 비용이 발생하는 서버리스 방식이 더 적합하다고 생각했다.

그래서 Google Cloud Run을 선택했다.

Cloud Run을 선택한 이유는 크게 세 가지였다.

첫 번째는 별도 도메인을 구매하지 않아도 기본 URL로 서비스를 사용할 수 있다는 점이다.

아직 MVP 단계이기 때문에 처음부터 도메인 비용을 쓰기보다, 실제 사용 가능성을 먼저 확인하는 것이 낫다고 생각했다. 나중에 정식 도메인이 필요해지면 그때 연결할 수 있다.

두 번째는 HTTPS 인증서를 직접 관리하지 않아도 된다는 점이다.

Compute Engine에 직접 배포하면 인증서를 설정하고 만료 전에 갱신하는 작업도 관리해야 한다. 보통 인증서 갱신을 자동화할 수는 있지만, 설정이 잘못되거나 갱신이 실패하는 경우도 확인해야 한다.

Cloud Run의 기본 도메인은 HTTPS가 적용되고 인증서 관리도 Google에서 처리한다. 3개월마다 인증서 갱신 여부를 직접 확인하지 않아도 되는 점이 실제 운영에서 편하다고 생각했다.

세 번째는 예상 사용자 수를 기준으로 비용이 더 적을 것이라고 판단했기 때문이다.

FaithLog는 최대 600명 규모를 예상하고 있다. 이 정도 규모에서 항상 실행되는 VM을 유지하는 것보다, 요청이 있을 때만 컨테이너가 실행되는 Cloud Run이 비용 면에서 더 유리할 것으로 예상했다.

물론 요청이 없던 뒤 첫 요청에서 인스턴스가 시작되면 응답이 느려질 수 있다. 하지만 현재 단계에서는 약간의 cold start보다 고정 서버 비용과 운영 부담을 줄이는 것이 더 중요하다고 판단했다.

이번 배포에서는 단순히 서버를 쉽게 띄우기 위해 서버리스를 선택한 것이 아니다. 예상 트래픽, 사용자 수, 도메인과 인증서 관리 비용까지 같이 고려한 결과였다.

## 성능도 일단 한 번 측정해봤다

테스트 수, 커버리지, API 응답시간을 정기적으로 기록하기 시작했다. Cloud Run의 읽기 API 기준으로 30 VU, 5분 부하를 실행했고 실패율 0%를 확인했다. 당시 p95는 약 257ms였다.

처음에는 응답시간 숫자만 기록하면 될 것 같았다.

하지만 같은 API라도 환경과 데이터 크기, 요청 수에 따라 결과가 달라질 수 있었다. 그래서 이후부터는 VU, 실행 시간, 데이터 조건을 같이 기록하기로 했다.

## 닫힌 투표에서 내 선택이 보이지 않았다

투표가 닫히면 결과만 보여주는 구조에서는 사용자가 자신이 무엇을 선택했는지 확인하기 어려웠다. 종료된 투표에서도 본인의 선택과 결과를 함께 볼 수 있도록 응답 계약을 보완했다.

상태값은 저장된 값만 믿지 않고 현재 시각과 시작·종료 시각을 함께 고려하도록 했다. 스케줄러가 약간 늦더라도 API가 잘못된 투표 상태를 반환하지 않게 하기 위해서다.

## 커피 투표를 정산까지 연결했다

커피 투표를 단순 설문이 아니라 실제 정산으로 연결했다.

1. 캠퍼스에서 커피 담당자를 지정한다.
2. 담당자가 메뉴 투표를 연다.
3. 멤버들이 메뉴를 선택한다.
4. 투표를 닫으면 선택 결과로 청구 항목을 만든다.
5. 담당자와 멤버가 미납 내역을 확인한다.

이 과정에서 투표 권한과 계좌 소유권이 섞이지 않도록 분리했다. 투표를 만들 수 있다고 해서 모든 납부 계좌를 수정할 수 있는 것은 아니기 때문이다. 정산이 중간에 실패하면 일부 청구만 남지 않도록 전체 과정을 하나의 트랜잭션으로 묶었다.

중복 요청도 같이 확인했다. 투표 종료 API가 두 번 호출되더라도 같은 사람에게 청구가 두 개 생기면 안 됐다. 그래서 이미 생성된 청구를 source type과 source ID로 확인하고, 중간 실패 시에는 전체 정산이 rollback되는 테스트를 추가했다.

기도모임도 시즌과 그룹 단위로 관리할 수 있게 확장했다. 모임이 없는 주와 아직 작성하지 않은 상태를 같은 `null`로 처리하지 않고 도메인 상태로 구분했다.

## 중간에 막혔던 부분

테스트와 문서 생성 작업이 동시에 실행될 때 Gradle과 Asciidoctor의 산출물 잠금이 충돌했다. 실행 순서만 바꾸면 잠시 사라졌지만 재발 가능성이 남았다. 그래서 공유 산출물을 사용하는 작업을 직렬화하고, CI에서도 같은 경계를 유지하도록 정리했다.

이번 작업을 하면서 기능 목록과 실제 사용 흐름은 다르다는 것을 느꼈다.

API 명세에 기능이 모두 있어도 중간 단계가 자연스럽게 이어지지 않으면 사용하기 불편할 수 있다.

다음에는 테스트 데이터를 더 많이 넣어보려고 한다. 지금은 데이터가 적어서 대부분 빠르게 동작하는데, 사용자가 늘어나도 같은지 확인해봐야 할 것 같다.
