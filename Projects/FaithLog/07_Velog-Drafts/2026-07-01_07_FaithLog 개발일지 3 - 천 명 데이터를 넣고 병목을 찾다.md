# [FaithLog 개발기 6] 사용자 1,000명 기준으로 성능을 확인했다

이번 기록은 평소 개발 일지라기보다는 성능 테스트를 처음 제대로 해본 기록에 가깝다.

테스트 데이터가 몇 개 없을 때는 모든 API가 빨랐다. 그래서 이 상태에서 성능이 괜찮다고 판단해도 되는지 궁금했다.

일단 사용자 1,000명을 넣어보기로 했다.

## 테스트 전에 정리한 것

벌금 계좌와 커피 계좌가 늘어나면서 “누가 어떤 계좌를 볼 수 있고 수정할 수 있는가”가 복잡해졌다. 계좌 종류만으로 권한을 판단하지 않고 캠퍼스, 소유자, 용도, 활성 상태를 함께 검증하도록 계약을 정리했다.

사용자 화면에는 본인에게 필요한 계좌만 노출하고, 관리자 조회와 멤버 조회의 응답도 분리했다. 비활성 계좌는 신규 청구에 사용하지 않지만 기존 청구의 이력은 유지했다.

## 처음 확인한 문제

기도제목과 투표 조회에서 반복 쿼리가 발생하는 지점을 발견했다. 목록 하나를 반환하기 위해 작성자, 응답 수, 선택 정보 등을 행마다 다시 조회하고 있었다.

목록을 조회할 때 필요한 관계를 묶어서 가져오고, 응답 수처럼 계산이 필요한 값도 한 번에 조회하도록 수정했다.

그리고 로컬 Docker Compose 환경에서 30 VU로 5분 동안 실행해봤다.

결과는 다음과 같았다.

- 평균 응답시간: 16.93ms
- p50: 8.47ms
- p95: 44.60ms
- p99: 89.37ms
- 처리량: 초당 약 295.92 요청
- 실패율: 0%

테스트는 한 번 실행하고 끝내지 않았다. 같은 데이터 수와 VU, 실행 시간을 다시 사용할 수 있도록 시나리오와 실행 ID를 남겼다. 나중에 쿼리를 수정했을 때 정말 빨라졌는지 같은 조건으로 비교하기 위해서다.

결과는 생각보다 괜찮았다.

다만 이 숫자만 보고 성능이 충분하다고 말하기는 어렵다. 데이터와 요청 시나리오가 바뀌면 결과도 달라지기 때문이다. 이후 다시 비교할 수 있도록 실행 ID와 데이터 조건도 같이 남겼다.

## 측정하고 나서 든 생각

처음에는 평균 응답시간만 확인했다.

그런데 평균값이 낮아도 일부 요청이 오래 걸릴 수 있다는 것을 알게 됐다. 그래서 p95와 p99도 같이 기록했다.

이번 결과는 로컬 환경에서 나온 값이라 운영 환경의 성능이라고 말할 수는 없다. 그래도 같은 조건으로 다시 실행할 수 있는 기준은 만들었다.

로컬 수치를 운영 성능처럼 적지 않는 것도 중요하다고 생각했다. 환경이 다른 숫자는 따로 기록하고, 비교 가능한 결과만 전후 수치로 사용하기로 했다.

다음에 코드를 수정하면 이 시나리오를 다시 실행해서 실제로 좋아졌는지 비교해볼 생각이다.
