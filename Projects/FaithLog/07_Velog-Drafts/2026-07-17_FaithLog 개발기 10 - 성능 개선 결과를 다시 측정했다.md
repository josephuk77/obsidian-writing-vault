# [FaithLog 개발기 10] 성능 개선 결과를 다시 측정했다

지난 글에서는 성능 테스트가 계속 무효가 됐던 과정을 정리했다.

측정 도중 PostgreSQL maintenance가 실행되거나, 같은 데이터셋에서 여러 부하를 연속으로 실행하면서 조건이 달라지는 문제가 있었다.

그래서 결과를 바로 성과로 사용하지 않고, 다시 실행할 수 있는 측정 기준부터 만들었다.

이번에는 그 기준을 사용해서 실제 성능 개선 결과를 측정했다.

## 먼저 전체 기능이 그대로 동작하는지 확인했다

성능을 개선하면서 기존 기능이 달라지면 안 됐다.

부하 테스트를 실행하기 전에 전체 테스트와 빌드, API 문서 생성을 먼저 확인했다.

- Gradle 전체 테스트 556개 통과
- 실패 0개, 오류 0개, 의도적으로 제외된 테스트 3개
- build 성공
- asciidoctor 성공
- 성능 측정 Node 계약 467개 중 466개 통과, 실패 0개, 의도적 skip 1개

성능만 좋아지고 정렬이나 권한, 응답 형식이 바뀌는 상황을 막기 위해서였다.

## 어떤 부분을 바꿨나

이번 측정에서는 사용자 목록과 캠퍼스 멤버 목록을 중심으로 확인했다.

기존 조회는 목록을 만든 뒤 사용자나 멤버십 정보를 반복해서 조회하는 부분이 있었다.

데이터가 적을 때는 잘 보이지 않았지만 1,000명 기준으로 조회하면 같은 종류의 쿼리가 계속 실행됐다.

그래서 필요한 사용자와 멤버십 정보를 한 번에 조회하도록 변경했다.

단순히 fetch join을 추가하는 것으로 끝내지 않았다. 기존 검색 조건, 정렬, 페이징, 캠퍼스 격리가 그대로 유지되는지도 같이 테스트했다.

## 측정 조건

이번에는 이전 결과와 비교할 수 있도록 조건을 고정했다.

- 사용자 1,000명 데이터셋
- 10 VU
- 2분 실행
- endpoint마다 개선 후 측정 3회
- 총 6회 실행
- 총 요청 수 99,873건
- correctness check 실패 0건
- HTTP 실패율 0%

한 번 잘 나온 결과를 고르지 않고, 세 번 측정한 p95의 중앙값을 사용했다.

## 관리자 사용자 목록 결과

개선 전 p95는 `339.366ms`였다.

개선 후 세 번의 p95는 다음과 같았다.

- `124.799ms`
- `125.903ms`
- `178.719ms`

중앙값은 `125.903ms`였다.

| 항목 | 개선 전 | 개선 후 중앙값 | 변화 |
| --- | ---: | ---: | ---: |
| p95 | 339.366ms | 125.903ms | 62.9% 감소 |
| 처리량 | 42.156 req/s | 113.935 req/s | 170.3% 증가 |

처리량은 약 2.70배가 됐다.

## 캠퍼스 멤버 전체 목록 결과

개선 전 p95는 `338.119ms`였다.

개선 후 세 번의 p95는 다음과 같았다.

- `98.682ms`
- `86.699ms`
- `103.321ms`

중앙값은 `98.682ms`였다.

| 항목 | 개선 전 | 개선 후 중앙값 | 변화 |
| --- | ---: | ---: | ---: |
| p95 | 338.119ms | 98.682ms | 70.8% 감소 |
| 처리량 | 42.910 req/s | 169.126 req/s | 294.1% 증가 |

처리량은 약 3.94배가 됐다.

## 한 번의 좋은 결과만 사용하지 않은 이유

성능 측정은 실행할 때마다 조금씩 달라질 수 있다.

실제로 관리자 사용자 목록의 개선 후 p95도 `124.799ms`에서 `178.719ms`까지 차이가 있었다.

가장 좋은 값만 선택하면 실제보다 개선 폭이 크게 보일 수 있다.

그래서 같은 조건에서 세 번 실행하고 중앙값을 사용했다. 실패율과 correctness check도 함께 확인했다.

또한 이 수치는 로컬의 shared-stack 측정 결과다.

운영 환경의 SLO나 최대 처리량을 의미하지 않는다. 동일한 환경에서 개선 전후를 비교한 결과로만 사용한다.

## 아직 남은 성능 개선

이번 통합 작업에는 정산, 관리자 청구 조회, 기도·투표 조회, 경건생활 조회, 알림 batch, 관리자 대시보드 최적화도 포함되어 있다.

하지만 모든 기능의 개선률을 한 글에서 주장하지 않기로 했다.

동일한 조건의 before와 after가 모두 확보된 사용자 목록과 캠퍼스 멤버 목록만 이번 결과에 포함했다.

기도 그룹 조회에서는 요청당 SQL이 약 586개 발생하는 새로운 병목 후보도 확인했다. 이 부분은 별도의 측정과 개선이 필요하다.

이번 작업을 하면서 성능 개선 코드보다 전후 결과를 믿을 수 있게 만드는 과정이 더 중요하다는 것을 느꼈다.

앞으로도 단순히 쿼리 수를 줄였다는 이유로 개선됐다고 판단하지 않고, 같은 데이터와 같은 부하에서 다시 측정한 결과를 남기려고 한다.
