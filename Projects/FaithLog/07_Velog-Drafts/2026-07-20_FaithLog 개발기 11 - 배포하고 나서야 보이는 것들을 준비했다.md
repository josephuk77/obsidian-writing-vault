# [FaithLog 개발기 11] 배포하고 나서야 보이는 것들을 준비했다

기능을 거의 다 만들고 나니 오히려 걱정이 하나 늘었다.

내 휴대폰에서 잘 동작하는 것과 실제 사용자 휴대폰에서 계속 잘 동작하는 것은 다른 문제였다. 배포한 뒤 오류가 나도 사용자가 직접 알려주기 전까지 모른다면 운영이라고 보기 어려웠다.

그래서 이번에는 화면을 더 만드는 대신, 출시 후 앱의 상태를 확인할 수 있는 장치를 넣었다.

## 강제 업데이트가 필요한 상황을 먼저 생각했다

모바일 앱은 서버처럼 배포 즉시 모든 사용자가 같은 버전을 쓰지 않는다. 스토어 심사가 끝나도 업데이트하지 않은 사용자는 이전 앱을 계속 사용한다.

백엔드 응답 형식이 바뀌거나 오래된 앱에 치명적인 문제가 생겼을 때, 사용자에게 업데이트를 안내할 방법이 필요했다.

Firebase Remote Config를 이용해 최소 지원 버전과 권장 버전을 원격에서 관리하도록 했다.

- 현재 버전이 최소 지원 버전보다 낮으면 업데이트가 필요하다는 화면을 보여준다.
- 권장 버전보다 낮은 정도라면 사용자가 나중에 업데이트할 수 있게 한다.
- 설정을 가져오지 못했다고 앱 전체가 막히지는 않도록 실패 정책도 따로 정했다.

여기서 중요했던 건 업데이트 팝업 하나를 만드는 것이 아니었다. 원격 설정이 늦게 오거나 실패하는 경우, 같은 안내가 반복되는 경우, 스토어로 이동했다가 돌아오는 경우까지 상태를 나눠야 했다.

정책과 화면을 분리하고 테스트를 붙였다. 덕분에 나중에 버전 기준이 달라져도 UI 코드를 다시 건드리지 않고 운영할 수 있게 됐다.

## 분석 이벤트에는 필요한 정보만 남겼다

다음은 Firebase Analytics였다.

어떤 화면이 실제로 사용되는지, 주요 작업이 성공했는지를 모르면 다음 개선 순서를 감으로 정하게 된다. 그렇다고 교회 앱에서 사용자 이름이나 기도 내용처럼 민감할 수 있는 정보를 이벤트에 넣을 수는 없었다.

그래서 이벤트 규칙부터 만들었다.

화면 이름, 기능 종류, 성공 여부처럼 제품 개선에 필요한 정보만 전송하고 자유 입력 내용과 개인 식별 정보는 제외했다. API 요청도 모든 호출을 기록하지 않고, 사용자가 실제로 완료한 주요 흐름 위주로 성공 이벤트를 남겼다.

데이터를 많이 모으는 것보다 왜 모으는지 설명할 수 있는 데이터만 남기는 편이 맞다고 생각했다.

## Crashlytics를 붙이고 끝내지 않았다

Crashlytics도 추가했다. 배포 환경에서 발생한 예외와 비정상 종료를 확인하기 위해서다.

다만 SDK 설치만 하고 끝내면 설정이 빠진 빌드가 나갈 수 있다. 그래서 Firebase 설정과 네이티브 연결 여부를 검사하는 테스트를 같이 추가했다.

로그인 세션을 확인하는 동안 빈 화면처럼 보이던 부분도 앱 로고가 나오도록 바꿨다. 짧은 시간이지만 앱을 처음 실행했을 때 사용자가 가장 먼저 보는 구간이라 그냥 두고 싶지 않았다.

## 이번 작업에서 달라진 생각

처음에는 배포를 개발의 마지막 단계라고 생각했다.

지금은 조금 다르게 생각한다. 배포는 내가 직접 보지 못하는 환경에서 앱이 실행되기 시작하는 시점이다. 그래서 업데이트 정책, 장애 확인, 사용 흐름 분석이 기능 구현만큼 중요했다.

이번에 추가한 장치가 오류를 없애주지는 않는다. 대신 오류를 늦게 알게 되는 시간을 줄여주고, 다음에 무엇을 고칠지 근거를 남겨준다.

배포 가능한 앱에서 운영 가능한 앱으로 넘어가는 작업이었다.
