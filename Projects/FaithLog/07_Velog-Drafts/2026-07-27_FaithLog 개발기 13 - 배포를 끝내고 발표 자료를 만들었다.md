# [FaithLog 개발기 13] 배포를 끝내고 발표 자료를 만들었다

FaithLog 배포를 모두 마쳤다.

기능 구현이 끝났을 때보다 스토어와 서버에서 실제 서비스가 동작하는 걸 확인했을 때 프로젝트가 끝났다는 느낌이 더 크게 들었다.

마지막 며칠은 새로운 기능보다 출시 빌드에서만 문제가 될 만한 부분을 정리하는 데 사용했다.

## Android 출시 빌드를 다시 봤다

개발 빌드는 디버깅하기 편한 대신 실제 출시 빌드와 조건이 다르다. 그래서 Android Release 설정을 따로 점검했다.

화면 회전과 크기 변경에 대응하도록 Activity 설정을 정리했고, 최신 Android의 edge-to-edge 화면에서 더 이상 권장되지 않는 system bar 속성도 제거했다.

R8 코드 축소와 사용하지 않는 리소스 제거를 켰다. 이후 기본 ProGuard 설정도 최적화 버전으로 전환하고 optimized resource shrinking을 명시했다.

Expo가 네이티브 프로젝트를 다시 생성해도 설정이 유지되도록 config plugin으로 만들었다. 생성된 Android 파일을 직접 고치면 다음 prebuild에서 사라질 수 있기 때문이다.

이 설정도 문자열 몇 줄을 추가한 것으로 끝내지 않고, 버전과 plugin 적용 여부, R8 설정을 검사하는 테스트를 붙였다.

## 첫 화면 이미지도 성능 문제였다

세션을 확인하는 동안 보여주는 로고는 잠깐만 나타난다. 처음에는 기존 아이콘 이미지를 그대로 사용했다.

그런데 짧게 보이는 화면에 큰 원본 bitmap을 올리는 건 낭비였다. 화면 밀도별 launch logo를 따로 만들고 실제 표시 크기에 맞는 이미지를 사용하도록 바꿨다.

눈에 띄는 새 기능은 아니지만 앱 시작 구간의 메모리와 이미지 처리 비용을 줄이는 작업이었다. 성능 개선은 서버의 p95만 보는 일이 아니라 사용자가 처음 마주치는 한 장의 이미지에서도 시작된다는 걸 느꼈다.

## 의존성과 백엔드 배포 경로도 마지막으로 확인했다

프론트에서는 Expo 관련 의존성을 업데이트하고 출시 버전을 `0.2.2`로 맞췄다.

백엔드에서는 배포 인프라와 공급망을 다시 감사했다. 이전에 확인했던 Spring Security 문제는 Spring Boot `3.5.15`, Spring Security `6.5.11`로 올라가면서 해결된 상태였다. 운영 health 요청도 `200 UP`과 보안 헤더를 확인했다.

반대로 아직 남은 것도 기록했다.

`main`, `develop` 브랜치 보호 규칙이 없고, Gradle dependency locking과 검증 metadata, 컨테이너 digest 고정, GitHub Action SHA 고정은 추가 보강이 필요하다. 확인하지 못한 Cloud Console 설정은 추측해서 통과 처리하지 않았다.

배포 전 점검이라고 해서 무조건 “문제없음”이라는 결론을 만드는 것보다, 확인된 것과 확인하지 못한 것을 나누는 편이 더 중요했다.

시간에 따라 달라지는 청구 조회 테스트도 고정 시각 fixture를 사용하도록 바꿨다. 자정이나 날짜 경계에서만 깨지는 테스트를 그대로 두면 배포 판단 자체를 믿기 어렵기 때문이다.

## 실제 배포를 마쳤다

백엔드는 Google Cloud Run에 배포했고, 프론트 앱도 출시 배포를 완료했다.

Cloud Run을 선택한 이유는 이전 글에 적었듯 예상 사용자가 최대 약 600명이고 요청이 항상 일정하게 들어오는 서비스가 아니기 때문이다. 컴퓨팅 인스턴스를 계속 켜 두는 것보다 요청량에 따라 동작하는 서버리스가 현재 규모에서는 비용 면에서 맞다고 판단했다.

기본 제공 주소로 시작할 수 있어 별도 도메인 비용을 당장 쓰지 않아도 되고, HTTPS 인증서를 직접 발급하거나 주기적으로 갱신하지 않아도 된다는 운영상의 장점도 컸다.

물론 서버리스가 항상 정답은 아니다. 트래픽이 지속해서 많아지거나 cold start가 중요한 문제가 되면 최소 인스턴스와 비용 구조를 다시 계산해야 한다. 이번 선택은 “서버리스가 좋아서”가 아니라 현재 사용자 규모와 운영 여건에 맞춘 결정이다.

## 코드를 발표 자료로 옮기면서

배포를 마친 뒤 발표용 PPT도 만들었다.

처음에는 구현한 기능을 최대한 많이 넣으려고 했다. 그런데 슬라이드에 기능 목록만 늘어놓으니 내가 어떤 문제를 해결했는지가 잘 보이지 않았다.

그래서 발표에서는 기능 수보다 판단의 근거가 남는 내용을 중심으로 정리했다.

- 왜 교회 운영 흐름을 앱으로 만들었는지
- 프론트와 백엔드를 어떤 기준으로 나눴는지
- 1,000명 데이터로 어떤 병목을 발견했는지
- p95와 처리량을 어떤 조건에서 비교했는지
- Cloud Run을 왜 선택했는지
- 배포 전 보안과 운영 문제를 어떻게 확인했는지

성능 개선 수치도 가장 잘 나온 한 번의 값이 아니라 세 번 측정한 중앙값과 측정 한계를 같이 적었다. 관리자 사용자 목록은 p95가 `339.366ms`에서 `125.903ms`로 줄었고, 캠퍼스 멤버 목록은 `338.119ms`에서 `98.682ms`로 줄었다. 다만 이 결과가 운영 환경의 최대 처리량을 보장하는 수치는 아니라는 설명도 넣었다.

PPT를 만들면서 프로젝트를 다시 설명해 보니, 코드에서는 잘 보이지 않던 흐름이 보였다.

기능 구현, 트러블슈팅, 성능 측정, 보안 점검, 배포가 따로 떨어진 일이 아니었다. 실제 사용자가 쓰는 서비스를 만들기 위해 순서대로 필요한 일이었다.

## 마무리

FaithLog는 처음부터 완벽한 설계로 시작한 프로젝트가 아니다.

기능을 만들면서 API 계약이 부족한 부분을 고쳤고, 데이터가 늘어난 뒤에 병목을 찾았고, 성능 수치를 믿기 위해 테스트 방식도 여러 번 버렸다. 배포 직전에는 기능보다 버전 호환, 장애 확인, 보안, 빌드 설정을 더 오래 봤다.

이번 프로젝트를 통해 가장 크게 배운 것은 “동작한다”와 “운영할 수 있다” 사이에 생각보다 많은 일이 있다는 점이다.

이제 개발 일지는 여기서 마무리하지만, 실제 사용이 시작되면 Analytics와 Crashlytics를 보면서 다시 고칠 부분이 생길 것이다. 배포 완료를 끝이라기보다 첫 운영 버전의 시작으로 남겨두려고 한다.
