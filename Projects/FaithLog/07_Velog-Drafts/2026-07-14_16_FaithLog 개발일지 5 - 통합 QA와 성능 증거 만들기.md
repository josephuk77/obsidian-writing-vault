# [FaithLog 개발기 8] 통합 테스트와 성능 측정을 진행했다

이번 주는 테스트를 실행하고, 실패 원인을 찾고, 다시 실행하는 일을 계속 반복했다.

기능 구현보다 측정 환경을 맞추는 데 시간이 더 많이 들었다.

처음 계획은 단순했다.

1. 현재 정산 성능을 측정한다.
2. 반복 조회를 줄인다.
3. 같은 조건으로 다시 측정한다.
4. 전후 결과를 비교한다.

하지만 실제로는 1번부터 생각대로 되지 않았다.

## 먼저 통합 테스트부터 진행했다

주간 경건생활 관리자 조회, 식사 담당 투표와 정산, 벌금 취소·재제출 흐름을 통합했다. 각각의 기능 테스트는 통과했지만 합치자 상태 전이와 정렬 순서, 기존 청구 보존 규칙이 충돌했다.

관리자가 이미 완납 처리한 벌금은 사용자가 기록을 취소하고 다시 제출해도 자동으로 되돌리지 않도록 결정했다. 자동 계산보다 실제 운영자가 확정한 납부 상태를 우선한 것이다.

통합 기준으로 449개 테스트가 실패 없이 완료됐고, Docker 환경에서 45단계 HTTP QA를 수행했다. 당시 JaCoCo 기준 Line coverage는 94.41%, Branch coverage는 75.77%였다.

커버리지 숫자를 올리기 위해 테스트를 추가한 것은 아니다. 경건생활 취소 뒤 벌금 상태, 식사 정산 중복 요청처럼 실제로 갈라지는 분기를 먼저 테스트했고, 결과적으로 어느 정도가 검증됐는지 확인하는 용도로 커버리지를 사용했다.

## 성능 테스트가 계속 무효가 됐다

투표 정산 성능의 기준선을 만들기 위해 1,000명의 사용자와 34개의 투표, 34,000개의 응답을 가진 데이터셋을 준비했다. 하지만 측정 과정에서 예상보다 많은 환경 변수가 나타났다.

- 측정 도중 PostgreSQL autovacuum과 autoanalyze가 실행됨
- Hikari 연결이 정상적으로 교체되며 PID가 달라짐
- 여러 측정 모드를 연속 실행하면서 앞선 쓰기가 다음 측정에 영향을 줌
- k6 v2 결과 형식과 기존 요약 파서가 맞지 않음
- Docker 메모리 값의 반올림과 수집 주기 차이

처음에는 문제가 생긴 실행도 참고용으로 사용할 수 있지 않을까 생각했다.

하지만 측정 도중 DB 상태가 바뀌었다면 이전 결과와 같은 조건이라고 보기 어려웠다. 이런 숫자를 기준으로 사용하면 실제보다 개선된 것처럼 보일 수도 있었다. 그래서 조건이 바뀐 실행은 결과에서 제외하고 실행 ID도 다시 사용하지 않았다.

실패한 실행을 계속 보면서 한 데이터셋으로 네 가지 부하를 연속 측정하는 방식에 문제가 있다는 것을 알게 됐다.

결국 부하마다 새로운 데이터셋을 만들도록 바꿨다.

- 커피 정산 순차 요청
- 식사 정산 순차 요청
- 커피 정산 동시 요청
- 식사 정산 동시 요청

각 실행 전에 데이터와 DB 상태를 검증하고, 결과 파일의 해시와 소스 커밋까지 묶어 증거를 남겼다. 이 기준선은 최적화 성과가 아니라 이후 결과와 비교하기 위한 `before` 자료로만 사용했다.

## 측정만 하다가 끝낼 수는 없어서 로직도 수정했다

기존 정산은 응답마다 계좌와 기존 청구를 반복 조회했다. 정산 명령을 모아서 전달하고, 계좌는 한 번 검증한 뒤 기존 청구도 source ID 집합으로 한 번에 잠금 조회하도록 변경했다.

중복 방지, 트랜잭션 롤백, 기존 완납 상태 보존 같은 도메인 규칙은 유지했다. 변경 후 전체 556개 테스트가 실패 없이 완료됐지만, 동일한 환경의 `after` 측정 전까지는 개선률을 주장하지 않기로 했다.

쿼리 호출 구조는 줄었지만 테스트가 통과했다는 사실만으로 성능 개선이라고 말할 수는 없었다. 실제 개선률은 같은 데이터와 부하로 다시 측정한 뒤에만 기록하기로 했다.

## 현재 남은 것

최신 체크아웃 브랜치에서는 Billing 응답 계약 관련 테스트 두 개가 실패하고 있다. 통합선의 마지막 완전 검증 결과와 현재 브랜치 결과가 다르기 때문에 둘을 섞어 말하지 않고 별도로 기록했다.

Docker 컨테이너 내부 헬스체크는 성공하지만 호스트의 매핑 포트로는 접속되지 않는 문제도 남아 있다. 컨테이너가 `Up`이라는 사실과 사용자가 실제로 접근할 수 있다는 사실은 다르므로 두 신호를 분리해 보고 있다.

솔직히 이번에는 성능 개선 자체보다 측정 준비에 더 많은 시간을 사용했다.

처음에는 k6를 실행하고 p95만 비교하면 될 줄 알았다. 실제로 해보니 테스트 데이터, DB maintenance, connection 상태, 실행 순서가 모두 결과에 영향을 줬다.

아직 최적화 이후 수치는 측정하지 못했다. 지금 억지로 개선률을 적기보다는 같은 조건을 만든 뒤 다시 실행하는 것이 맞다고 생각했다.

다음 작업은 다음과 같다.

- Billing 테스트 실패 2개 확인
- 호스트에서 Docker 포트에 접근되지 않는 문제 확인
- 통합 브랜치에서 최적화 이후 성능 측정
- PostgreSQL 실행 계획 확인

이번 주 일지는 깔끔하게 끝난 작업보다는, 왜 측정이 생각보다 어려웠는지를 남기는 기록이 됐다.
