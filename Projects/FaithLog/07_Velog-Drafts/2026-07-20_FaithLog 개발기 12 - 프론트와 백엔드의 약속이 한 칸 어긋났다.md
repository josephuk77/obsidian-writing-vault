# [FaithLog 개발기 12] 프론트와 백엔드의 약속이 한 칸 어긋났다

배포 전 투표 기능을 확인하다가 이상한 상황을 만났다.

사용자가 직접 항목을 추가할 수 있는 투표가 있고, 관리자가 만든 항목만 선택해야 하는 투표가 있다. 그런데 어떤 화면에서는 항목 추가 버튼이 보이고, 어떤 화면에서는 같은 투표인데도 보이지 않았다.

처음에는 프론트 조건문 문제라고 생각했다.

결론부터 말하면 프론트만의 문제도, 백엔드만의 문제도 아니었다. 둘 사이의 약속이 한 칸 어긋나 있었다.

## 응답에 필요한 값이 없었다

백엔드에는 `사용자 항목 추가 허용 여부`가 이미 존재했다. 투표를 만들 때는 저장되고 있었지만, 투표 목록과 상세 조회 응답에는 그 값이 노출되지 않는 경로가 있었다.

프론트는 서버가 주지 않은 값을 알 수 없으니 화면에서 일관된 판단을 할 수 없었다.

백엔드의 목록 응답과 상세 응답에 허용 값을 추가하고, 서비스 결과 객체와 REST Docs까지 같이 맞췄다. 단순히 DTO 필드 하나만 넣으면 내부 변환 과정에서 빠질 수 있어서 컨트롤러 문서 테스트로 실제 응답 계약을 고정했다.

## 값이 추가된 뒤에도 바로 끝나지 않았다

새 백엔드만 생각하면 boolean 값을 그대로 사용하면 된다.

하지만 이미 설치된 앱이나 이전 mock 데이터에서는 해당 필드가 아예 없을 수 있었다. 이때 누락 값을 무조건 `false`로 처리하면 과거에 동작하던 투표에서 갑자기 기능이 사라질 수 있다.

프론트에서는 새 응답을 우선 사용하되, 필드가 없는 이전 응답도 안전하게 처리하는 호환 규칙을 만들었다. 이후 목록 필터, 상세 화면, mock adapter, runtime validation이 같은 규칙을 사용하도록 정리했다.

## 항목 추가 요청끼리 섞이는 문제도 있었다

테스트를 더 돌리면서 다른 문제도 발견했다.

mock 환경에서 여러 투표의 항목 추가가 연달아 실행되면 한 투표의 변경 상태가 다른 투표 작업에 영향을 줄 수 있었다. 실제 API처럼 요청 단위를 독립적으로 다루지 못한 것이 원인이었다.

항목 추가 작업의 상태를 투표별로 분리하고, 연속 요청에서도 각각의 결과가 유지되는 테스트를 추가했다.

화면에서 버튼 하나가 잘못 보인 문제였지만 확인 범위는 다음까지 넓어졌다.

- 백엔드 목록·상세 응답
- 서비스 결과와 DTO 변환
- REST Docs 계약
- 프론트 runtime validation
- 이전 응답과의 호환
- mock 환경의 요청 격리
- 응답자 정보 노출 여부

## 이번에 배운 점

API 연동 문제를 볼 때 어느 한쪽 코드만 보고 책임을 정하면 해결이 늦어진다.

백엔드에 값이 존재하는지, 응답으로 실제 전달되는지, 프론트가 누락과 명시적 `false`를 구분하는지까지 하나의 흐름으로 봐야 했다.

특히 `false`와 `필드 없음`은 같은 값처럼 보여도 버전이 다른 앱과 서버가 만나는 순간 의미가 달라진다.

이번 수정은 기능을 새로 만든 작업은 아니었다. 대신 배포된 여러 버전이 동시에 존재할 수 있다는 전제로 계약을 다듬었다. 실제 운영에서는 이런 작은 경계가 더 오래 남는 문제를 만든다는 걸 확인했다.
