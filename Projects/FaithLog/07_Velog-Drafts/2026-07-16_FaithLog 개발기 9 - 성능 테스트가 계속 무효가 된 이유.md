# [FaithLog 개발기 9] 성능 테스트가 계속 무효가 된 이유

이번에는 투표 정산 로직을 개선하기 전에 성능을 먼저 측정해보려고 했다.

계획은 단순했다.

1. 현재 성능을 측정한다.
2. 반복 조회를 줄인다.
3. 같은 조건으로 다시 측정한다.
4. 전후 결과를 비교한다.

처음에는 k6를 실행하고 p95만 비교하면 될 줄 알았다.

하지만 실제로 해보니 1번부터 생각대로 되지 않았다.

## 첫 번째 측정

사용자 1,000명과 투표 34개, 응답 34,000개를 만들었다.

순차 요청과 동시 요청 모두 실패율은 0%였다. 결과만 보면 그대로 기준값으로 사용해도 될 것 같았다.

그런데 측정 시간과 PostgreSQL 상태를 같이 확인해보니 중간에 autovacuum과 autoanalyze가 실행됐다.

측정 도중 DB 상태가 바뀌었기 때문에 이전과 같은 조건이라고 보기 어려웠다. 첫 번째 결과는 사용하지 않기로 했다.

## 두 번째 측정

이번에는 DB maintenance가 없는 시간을 확인한 뒤 다시 실행했다.

하지만 HikariCP의 연결이 정상적으로 교체되면서 PostgreSQL backend PID가 바뀌었다. 처음 만든 검증 로직은 PID가 바뀌면 DB 상태가 달라졌다고 판단했다.

애플리케이션 문제는 아니었다. 같은 연결 풀 안에서 정상적으로 connection이 교체된 것이었다.

PID 자체가 아니라 database, user, application name, client address, state가 같은지를 비교하도록 기준을 바꿨다.

## 세 번째 측정

커피 순차 정산은 정상적으로 끝났다.

그다음 식사 순차 정산을 실행하려고 했는데 readiness 단계에서 계속 멈췄다. 앞선 커피 정산이 많은 데이터를 수정하면서 다음 autoanalyze 기준에 가까워졌기 때문이다.

한 데이터셋에서 여러 부하를 차례대로 실행하는 방식 자체가 문제였다.

그래서 측정을 다음 네 가지로 분리했다.

- 커피 순차 정산
- 식사 순차 정산
- 커피 동시 정산
- 식사 동시 정산

각 테스트는 새로운 데이터셋을 만들고 하나의 부하만 실행하도록 했다.

## 그 뒤에도 바로 끝나지는 않았다

측정 스크립트를 나누는 과정에서도 문제가 계속 나왔다.

- 테스트 환경변수가 실제 collector에 전달됨
- Bash local 변수를 선언하는 줄에서 아직 할당되지 않은 값을 참조함
- k6 v2 summary 구조와 기존 parser가 맞지 않음
- Docker stats의 메모리 값이 반올림됨
- 수집 주기 사이의 짧은 변화가 빠짐

문제가 생긴 실행은 결과가 일부 남아 있어도 모두 제외했다. 같은 실행 ID도 다시 사용하지 않았다.

수치가 잘 나온 실행도 조건이 달라졌다면 폐기했다. 좋은 결과를 남기는 것보다 다시 확인할 수 있는 결과를 남기는 편이 더 중요하다고 생각했다.

## 최종 before 측정

결국 네 가지 부하를 각각 새로운 데이터셋에서 실행했다. 모든 요청의 실패율은 0%였다.

| 구분 | p50 | p95 | p99 | 최대 |
| --- | ---: | ---: | ---: | ---: |
| 커피 순차 | 890.69ms | 1,117.25ms | 1,168.38ms | 1,181.16ms |
| 식사 순차 | 1,146.04ms | 1,294.68ms | 1,303.83ms | 1,306.12ms |
| 커피 동시 | 2,732.84ms | 4,330.26ms | 4,474.46ms | 4,510.51ms |
| 식사 동시 | 3,019.87ms | 6,293.26ms | 6,762.88ms | 6,880.29ms |

이 값은 성능이 좋다는 의미가 아니다.

최적화 전 상태를 같은 조건으로 다시 비교하기 위한 기준값이다. 자동으로 성과 수치로 사용하지 않고 `before` 자료로만 남겼다.

결과 파일에는 실행한 소스 커밋과 데이터셋 ID, 실행 ID, 대상 환경을 같이 묶었다. 네 가지 결과가 서로 다른 조건에서 섞이지 않았는지도 별도 검증했다.

## 아직 끝나지 않았다

정산 로직의 반복 조회는 줄였고 전체 테스트도 통과했다.

하지만 최적화 이후 측정은 아직 하지 않았다. 현재 통합 브랜치의 다른 회귀와 Docker 접근 문제를 먼저 정리해야 한다.

이번 작업에서 가장 오래 걸린 것은 코드를 빠르게 만드는 일이 아니라, 결과를 믿을 수 있는 조건을 만드는 일이었다.

다음에는 같은 방식으로 `after`를 실행하고 실제로 얼마나 달라졌는지 비교해보려고 한다.
