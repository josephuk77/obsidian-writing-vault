# [FaithLog 개발기 4] 백엔드 구현을 시작했다

FaithLog의 기획과 ERD, API 설계를 어느 정도 마치고 이번 주부터 실제 백엔드 구현을 시작했다.

처음에는 캠퍼스, 경건생활, 투표, 벌금 기능을 하나씩 만들면 될 것 같았다.

하지만 직접 구현해보니 생각보다 기능끼리 연결되는 부분이 많았다. 캠퍼스 권한을 먼저 확인해야 경건생활과 투표 데이터를 조회할 수 있고, 경건생활을 제출하면 벌금 청구까지 이어져야 했다.

## 6월 16일 — 구현 전에 규칙부터 고정했다

첫날에는 기능을 바로 만들기보다 구현할 때 지킬 기준부터 정리했다.

FaithLog는 실제 운영을 생각하고 있는 프로젝트다. 그래서 이슈마다 API 응답과 권한 범위를 먼저 정하고, 구현한 뒤에는 테스트 결과를 기록하기로 했다.

서비스 전체 권한과 캠퍼스 내부 역할도 분리했다. 서비스 관리자는 전체 사용자를 관리하지만, 캠퍼스 리더는 자신이 속한 캠퍼스 안에서만 역할을 수행한다. 이 구분은 이후 거의 모든 API의 인가 기준이 됐다.

이때 결정한 내용은 따로 decision log에 남겼다. 구현하면서 이전 문서와 충돌하는 내용이 생겼을 때 가장 최근에 확정한 결정을 기준으로 판단하기 위해서다. 코드만 관리하는 것이 아니라 왜 그렇게 구현했는지도 같이 남겨두고 싶었다.

## 6월 17일 — JWT 인증과 세션 수명주기

회원가입과 로그인, 토큰 재발급, 로그아웃을 구현했다. Access Token과 Refresh Token은 HttpOnly Cookie로 전달하고, 서버에는 Refresh Token 원문 대신 현재 세션을 식별하는 값을 Redis에 저장했다.

테스트에서는 예상하지 못한 문제가 나왔다. 인증 테스트와 다른 테스트가 같은 Spring Context를 공유하면서 Redis 관련 상태가 섞였다. 단순히 테스트 순서를 바꾸는 대신, 인증 상태가 테스트 간에 공유되지 않도록 컨텍스트와 저장소를 격리했다. 인증 기능은 성공 응답만 확인해서는 부족하고, 만료·로그아웃·재발급 실패까지 하나의 수명주기로 검증해야 한다는 점을 배웠다.

Controller 테스트, JWT 발급 테스트, Security Filter 통합 테스트의 역할도 나눴다. 한 테스트에서 전부 확인하면 실패했을 때 원인을 찾기 어려웠기 때문이다.

## 6월 18일 — 캠퍼스와 납부 도메인

캠퍼스 생성과 초대코드 가입, 멤버 역할 변경을 구현했다. 한 사용자가 여러 캠퍼스에 속할 수 있으므로 모든 조회와 변경은 `campusId`를 기준으로 소속 여부를 먼저 검증하도록 했다.

벌금과 커피비를 하나의 납부 흐름으로 다루기 위해 납부 계좌와 청구 항목의 기반도 만들었다. 계좌의 활성 상태, 청구 항목의 미납·완납 상태, 관리자 변경 권한을 각각 분리했다. 화면에서는 단순한 “납부 완료” 버튼이지만 백엔드에서는 허용 가능한 상태 전이인지 확인해야 했다.

## 6월 19일 — 경건생활 기록과 벌금 자동화

경건생활은 매일 체크할 수도 있고 일요일에 한 주 기록을 한 번에 제출할 수도 있다. 두 입력 경로가 같은 주간 기록을 수정하기 때문에 동기화 규칙을 먼저 정했다.

주간 제출이 끝난 뒤에는 누락 횟수와 지각 시간을 계산하고, 활성화된 벌금 규칙을 적용해 청구 항목을 생성했다. 같은 주차를 다시 제출했을 때 벌금이 중복 생성되지 않도록 중복 제출 계약도 테스트로 고정했다.

## 6월 20~22일 — 투표, 알림, 배치, 배포

투표 응답과 결과 조회, FCM 토큰과 알림 이력, Redis 기반 중복 방지 잠금을 구현했다. 같은 알림 배치가 여러 인스턴스에서 실행되더라도 한 번만 발송되도록 잠금 범위와 만료 시간을 정했다.

이후 캠퍼스 관리자 대시보드, 기도제목 게시판, 스케줄러를 추가하고 Cloud Run과 Supabase를 고려한 배포 구성을 정리했다. 권한이 변경된 사용자의 기존 토큰이 계속 유효한 문제를 발견해 토큰 버전 방식의 무효화도 도입했다.

## 이번 주를 마치며

이번 주에는 생각보다 많은 기능을 구현했다.

하지만 기능 개수보다 중요했던 것은 실제 운영 규칙을 코드와 테스트로 정리한 것이었다. 인증, 캠퍼스, 경건생활, 납부, 투표, 알림이 서로 연결되기 시작하면서 예외 상황도 많이 생겼다.

다음에는 기능을 따로 확인하는 것에서 끝내지 않고, 실제 사용 흐름대로 연결해서 테스트해보려고 한다.
